# OCR 페이지 병렬화 실제 provider 검증 — 2026-08-10

브랜치: `feature/case_ocr` (`c3938b6 perf(ocr): transcribe pages concurrently,
in source order`). 목적: fixture provider로 이미 확인된 병렬화 동작이 **실제
claude-cli provider와 실제 스캔 문서**에서도 성립하는지 검증.

## 대상과 격리 조건

`_source-cases/개인정보 마스킹 추가본/질병/질병5.pdf`
(sha256 `59ee3318da3430cf118a87eabd657ade742896178cc4c238552fc2c6feaabf2e`,
530,820 bytes, 12페이지).

- **순수 스캔**: 12페이지 전부 임베디드 텍스트 0자 (`page.get_text()` 확인).
  따라서 `run_ocr`의 born-digital 우회 경로가 `None`을 반환하고 12페이지 전부
  실제 vision OCR을 탄다. 출력의 `extraction_method`가 `embedded_text`가 아니고
  `cross_validation_mode`가 `single_technology_weak_p8_poc`인 것으로 재확인.
- **인테이크되지 않은 원본이며 손해사정서(답안지)**. 파이프라인에 투입하지 않음.
  `docs/case-type-axis-assignment-2026-08-07.md`가 이 파일을 뇌성마비진단담보
  (특별약관) 사정 건으로 분류해 두었고, `outputs/`에서 `질병5`를 참조하는 산출물은
  없음(= 미인테이크 확인).
- **DAO 쓰기 없음**: `ocr_extract.py`는 CLI로 실행하면 결과 JSON을 stdout으로만
  출력하고 계약 파일을 직접 쓰지 않는다. 검증 산출물은 전부 세션 scratchpad에
  저장했고, 저장소에는 gitignore된 `_ocr_scratch/`의 임시 파일만 생겼다가 종료 후
  삭제했다. 검증 전후 `git status`와 `outputs/`·`data/` untracked 조회 모두 비어

케이스 ID는 실제 케이스와 충돌하지 않도록 `CASE_OCRVERIFY_W1` /
`CASE_OCRVERIFY_W4` / `CASE_OCRVERIFY_INT`를 썼고, 검증 후 관련 scratch를 전부
삭제했다.

Provider: reader_a / reader_b / comparator 모두 `claude-cli` (기본값).
페이지당 3회 provider 왕복(독립 read 2회 + 비교 1회), 각 호출은
`claude -p --safe-mode` 자식 프로세스 1개.

## 1. 벽시계 시간 — 렌더링 제외 후 4.14배

| workers | 벽시계 | 렌더링(1.54s) 제외 |
|---|---|---|
| 1 | 580.67s | 579.13s |
| 4 | 141.32s | 139.78s |

**렌더링 제외 speedup 4.14배** (raw 4.11배). 2배 미만이 아니므로 provider 동시성
제한을 의심할 근거가 없고, 아래 3번에서 실제로 4개가 동시에 떠 있는 것을 직접
관측했다.

렌더링 기준선은 사용자가 준 1.54s를 그대로 썼다. 독립 측정에서는
`split_to_page_images()`가 12페이지 1.436s (0.120s/page)로 나와 사실상 일치하며,
어느 쪽을 써도 speedup은 4.1배대다.

4배를 약간 넘는 것은 이상현상이 아니다. 순차 실행에는 유난히 느린 페이지(측정 중
p5가 약 7분간 in-flight)가 전체를 직렬로 막는 구간이 있는데, 병렬 실행에서는 그
느린 페이지가 다른 페이지들과 겹쳐 흡수된다. 즉 순차 쪽이 지연 편차에 더 크게
손해를 본다.

주의: `rc=1`은 실패가 아니다. `main()`이 P8 불일치가 하나라도 있으면 1로 종료한다
(`sys.exit(1 if any_disagreement else 0)`). workers=1 실행은 p4/p7이 disagreed라
rc=1, workers=4 실행은 전부 agreed라 rc=0이었다. 두 실행 모두 12페이지 완주.

## 2. 페이지 순서와 reader 귀속 — 이상 없음

두 실행 모두 `pages[]`가 `[1,2,…,12]` 오름차순이고 길이 12.

내용 자체는 OCR 비결정성 때문에 완전히 일치하지 않으므로(문자 수가 페이지별로
수십 자 단위로 흔들림), **페이지 귀속**을 두 방법으로 확인했다.

**(a) 숫자 지문 대조.** 각 페이지에서 3자리 이상 숫자 토큰을 뽑아 두 실행을
비교했다. 12페이지 전부 일치 — p2의 `07805,242,1014,6958,6866,6008`,
p7의 `6561,9310,125,24620`처럼 페이지 고유값이 그대로 같은 번호에 붙어 있다.
어떤 페이지의 본문이 다른 번호로 들어갔다면 여기서 깨진다.

**(b) reader_a/reader_b 뒤바뀜 검사.** 페이지별로 정방향 쌍(a-a, b-b)과 교차
쌍(a-b, b-a)의 유사도를 비교했다. 교차 쪽이 뚜렷하게 높은 페이지는 없음
(`cross-better: none`).

p7/p8/p9에서 교차가 0.01 정도 높게 나왔으나 이는 뒤바뀜이 아니다. 같은 실행
안에서 reader_a와 reader_b가 이미 0.958~0.998로 서로 매우 닮아 있어서, 네 가지
비교값이 전부 같은 좁은 구간에 몰린다. 진짜 뒤바뀜이라면 `a1-b4`가 1.0에 가깝고
`a1-a4`가 확연히 낮아야 하는데 그런 패턴은 없다. (검사기 자체는 인위적으로
뒤바꾼 입력에 대해 `flag=True`를 내는 것을 먼저 확인했다 — 통과가 공허하지 않음.)

구조적으로도 뒤바뀜이 불가능하다. 병렬 단위는 페이지이고, 한 페이지의 두 read는
동일한 `img_path`를 받아 서로 순차로 실행된다. 결과는 완료 순서가 아니라
페이지 인덱스 슬롯(`slots[index]`)에 들어간다.

## 3. 동시 실행 4개 — rate limit / 프로세스 생성 오류 없음

**동시성 실측**: workers=4 실행 중 4초 간격 71회 샘플링. 최대 4,
분포 `{0:18, 1:5, 2:4, 4:43, 5:1}` — 43회가 정확히 4개로, 풀이 실제로 포화된다.
(`5`는 샘플링 경계 아티팩트로 종료 중인 자식과 새로 뜬 자식이 겹쳐 잡힌 1회.
0/1/2는 실행 종료 후 구간.)

**오류 없음**: 두 실행 모두

- `retried_calls = 0` (모든 호출 `attempts=1`)
- `nonzero_returncode = 0`
- `calls_with_stderr = 0`

호출 회계도 맞는다. 페이지 12 × 역할 3 = 36 중 33회가 실제 호출, 3회는
`identical_reads` 지름길이다 — 두 read가 바이트 단위로 같으면 `compare()`가
comparator 왕복을 건너뛴다(`comparator_called: false`). 미설명 누락 0.

이 회계는 처음에 틀렸다가 잡은 부분이다. 분석기가 `metadata` 키를 읽고 있었는데
실제 키는 `provider_metadata.<role>.raw_metadata.attempts`였고, 그대로 뒀으면 무슨
일이 일어났든 "재시도 0"이라고 보고했을 것이다. 그래서 총 호출 수를 기대값과
대조하고 미설명 누락을 따로 세도록 고쳤다.

측정 중 자식 PID가 20초 간격으로 바뀌는 것을 보고 재시도 루프로 잠깐 오판했는데,
해당 페이지의 `attempts`는 전부 1이었다. PID 교체는 재시도가 아니라 한 페이지의
세 호출(reader_a → reader_b → comparator)이 각각 새 자식을 띄우는 정상 동작이다.
재시도 여부는 PID 관찰이 아니라 `attempts` 필드로 판단해야 한다.

참고로 provider는 전송 오류에 대해 최대 3회 시도(`_CLAUDE_CLI_MAX_ATTEMPTS`,
2초 간격)를 하고 transcribe 호출 타임아웃은 180초다. 이번 측정에서는 재시도가
한 번도 발동하지 않았다.

## 4. 중단 후 재실행 — 완료 페이지 건너뜀

workers=4로 실행하다 resume 캐시에 4페이지가 쌓인 시점에 프로세스 트리를 강제
종료(`taskkill /F /T`, Windows에서는 부모만 죽이면 claude 자식이 살아남으므로
트리 종료)한 뒤 같은 명령을 재실행했다.

- 종료 후 캐시 잔존: `page_001~004.json` 4개
- 재실행 시 `(cached)` 보고: **4페이지** (1,2,3,4)
- 새로 전사한 페이지: **8페이지** (5~12)
- 성공 완주 후 캐시 디렉터리 자동 삭제: 확인 (`exists = False`)

재실행 출력도 `pages[]` 1..12 오름차순이고, 12페이지 전부 workers=1 기준선과
숫자 지문이 일치했다 — 중단 경계를 넘어서도 페이지 귀속이 유지된다.

캐시 보고 순서가 `3, 2, 4, 1`로 뒤섞여 나온 점이 오히려 설계가 의도대로 도는
증거다. 워커 스레드가 경쟁하며 보고하는데도 최종 `pages[]`는 소스 순서를 지킨다.

캐시는 페이지 번호로 키가 잡히고(`page_{page:03d}.json`), `.tmp` 기록 후
`replace`로 원자적 교체를 하므로 쓰기 도중 중단돼도 반쪽 페이지가 신뢰되지 않는다.

## 추가 측정 — workers=8 (기본값 상향 검토용)

기본값을 8로 올리는 것이 타당한지 묻는 질문이 나와, 같은 문서에 workers=8을
한 번 더 측정했다.

| workers | 벽시계 | 렌더링 제외 | speedup | 효율 | 페이지당 |
|---|---|---|---|---|---|
| 1 | 580.67s | 579.13s | 1.00x | 100% | 48.26s |
| 4 | 141.32s | 139.78s | 4.14x | 104% | 11.65s |
| 8 | 86.06s | 84.52s | **6.85x** | **86%** | 7.04s |

4→8 한계 이득은 **1.65배**(이상적 2.00배). 즉 8도 여전히 빨라지지만 선형이
아니고, 워커당 효율은 104% → 86%로 떨어진다.

정확성은 8에서도 문제 없음: `pages[]` 1..12 오름차순, 숫자 지문 12/12가 workers=1
기준선과 일치, 재시도 0 / 비정상 종료 0 / stderr 0, 호출 회계 36/36. 동시성
실측도 **최대 8 도달**(정확히 8인 샘플 10회)로 풀이 실제 포화됐다.

**그럼에도 기본값은 4 유지를 권한다.** 근거는 이 머신의 속도가 아니라 아래 두
가지다.

1. **provider에 rate limit 처리가 없다.** `llm_providers.py`에 429 / `Retry-After`
   / 지수 백오프에 해당하는 코드가 없고, 재시도는 **고정 2초 × 최대 3회**다
   (`_CLAUDE_CLI_RETRY_SLEEP_SECONDS = 2.0`). 8개가 동시에 한도를 건드리면 8개가
   거의 동시에 2초 후 재시도하고, 두 번 실패하면 페이지가 예외로 죽는다.
   한도는 머신이 아니라 계정에 걸리므로 이번 측정에서 재시도가 0이었다는 사실이
   다른 계정·다른 시간대의 안전을 보장하지 못한다.
2. **자식 1개당 메모리 약 395MB.** 8워커면 약 3.2GB다. 이 머신(22 논리 CPU,
   31.6GB, 여유 14.4GB)에선 여유롭지만 기본값은 가장 약한 실행 환경에서도
   안전해야 한다. CPU는 제약이 아니다(작업이 네트워크 대기라 22코어가 놀고 있다).

정리하면 8은 **이 머신에서 옵트인으로 쓰기 좋은 값**이지 기본값으로 바꿀 근거는
아직 부족하다. 대량 배치(예: 1,782페이지 코퍼스)를 돌릴 때는
`--workers 8` 또는 `HARNESS_OCR_WORKERS=8`로 그 실행에만 올리는 쪽이,
실패 시 8페이지가 함께 죽는 위험을 그 배치에만 한정한다는 점에서도 낫다.

기본값을 실제로 8로 올리려면 그 전에 재시도를 지수 백오프 + jitter로 바꾸고
429를 식별해 `Retry-After`를 존중하게 만드는 편이 순서상 맞다. 그 뒤라면 8은
합리적인 기본값이 된다.

### 후속: 백오프 구현 완료 (같은 날)

위 전제조건을 구현했다 (`tools/llm_providers.py`).

- 고정 2초 → **지수 백오프 + full jitter**: 대기 = `uniform(0, min(30, 2 * 2**(n-1)))`.
  상한 2s → 4s → 8s, cap 30s.
- **`Retry-After` 존중**: CLI 진단 텍스트에서 delta-seconds를 파싱해 그 값을
  대기의 하한으로 삼고, 그 위에 jitter를 더한다(대기 끝난 호출들이 다시 뭉치지
  않도록). 외부 값이므로 cap으로 clamp.
- **rate limit 식별**: `429`/`rate limit`/`too many requests`/`overloaded`/`529`/
  `quota exceeded`/`capacity`. 서브프로세스라 상태 코드가 없어서 자식이 출력한
  진단 문자열로 판정한다.
- 재시도 대상 구분은 그대로: `FileNotFoundError`는 즉시 raise(실제 provider로
  0.01s 확인), structured-output은 여전히 `max_attempts=1`(P4), P8 내용 불일치는
  무관.

효과 측정(8 워커가 동시 실패하는 상황): 재시도 도착 분산이 **0.00s → 1.18s
(1회차) / 3.16s (2회차) / 7.44s (3회차)**.

테스트 34개 추가(`tests/test_llm_provider_backoff.py`). 각 테스트는 결함을 실제로
되돌려 실패하는지 확인했다 — 상수 sleep 복원(8개 실패), **지수만 넣고 jitter 제거
(4개 실패)**, `Retry-After` 무시(3개 실패), 헬퍼는 맞는데 루프가 detail을 안 넘김
(1개 실패). 특히 두 번째와 네 번째가 중요한데, 겉보기엔 고쳐진 것처럼 보이면서
herd는 그대로 남는 형태이기 때문이다.

## 결론

네 가지 확인 항목 모두 실제 provider·실제 스캔에서 통과했다.

1. 렌더링 제외 **4.14배** (2배 미만 아님, provider 동시성 제한 근거 없음)
2. 페이지 순서 1..12 정상, reader 귀속 뒤바뀜 없음 (숫자 지문 12/12 일치)
3. 동시 4개 실측 포화, 재시도/비정상 종료/stderr 전부 0
4. resume 캐시가 완료 4페이지를 건너뛰고 8페이지만 재전사, 완주 후 자동 정리

부수 관찰: 이 문서는 workers=1에서 p4/p7이 disagreed, workers=4에서는 전부
agreed였다. 병렬화 때문이 아니라 이미 알려진 OCR 비결정성이다(같은 문서를 두 번
돌리면 서로 다른 페이지가 불일치하는 현상은 CASE_012/CASE_013에서 이미 관측된 바
있다). 병렬화는 벽시계 시간만 바꾸며, 실행 간 내용 차이는 병렬화 이전부터 있던
성질이다.
